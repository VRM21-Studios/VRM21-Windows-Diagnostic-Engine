# Limitations

## Overview

VRM21 Windows Diagnostic Engine is a read-only diagnostic and auditing framework.

Its results should be interpreted as system observations and heuristic assessments rather than authoritative hardware certification, security verdicts, or performance benchmarks.

Many Windows diagnostic interfaces expose incomplete, hardware-dependent, or approximate information.

## Windows and Hardware Dependency

Diagnostic availability depends on:

* Windows version
* PowerShell version
* Hardware vendor
* Firmware implementation
* Device drivers
* WMI/CIM providers
* Available performance counters
* Administrative privileges

A missing value does not necessarily indicate a hardware or software failure.

## CPU Diagnostics

### CPU Usage

The CPU module uses Windows performance-counter data to obtain usage information.

The reported values represent short snapshots rather than long-term workload characterization.

### Process CPU Information

`Get-Process.CPU` represents cumulative CPU time consumed by a process.

It should not be interpreted as an instantaneous CPU utilization percentage.

### Processor vs Core Terminology

Windows performance-counter instances may represent logical processors rather than physical CPU cores.

Consequently, some output described as per-core information may more accurately represent per-processor or per-logical-processor activity.

### Temperature

CPU temperature information may be obtained through ACPI thermal zones.

An ACPI thermal-zone value is not guaranteed to represent the CPU package or hottest CPU core sensor.

Temperature results should therefore be treated as approximate unless validated against hardware-specific sensor sources.

### Health Score

The CPU status classification uses heuristic thresholds.

It is not a standardized CPU health benchmark.

## GPU Diagnostics

### VRAM Reporting

The `AdapterRAM` value reported by Windows does not universally represent dedicated physical VRAM, particularly for integrated graphics and shared-memory architectures.

### Dedicated GPU Detection

Integrated/dedicated GPU classification uses module-specific heuristics.

GPU vendor naming and adapter configurations can produce classifications that require manual verification.

### GPU Utilization

The GPU performance counter is based on GPU engine activity.

It should not automatically be interpreted as a single total-GPU utilization percentage.

### Graphics Process Detection

The graphics-process list is based on predefined process names.

A listed process is not necessarily consuming significant GPU resources, and a process not on the list may still use the GPU.

### GPU Temperature

GPU temperature discovery is dependent on available WMI/firmware information.

Generic temperature providers may not expose a validated GPU sensor or may expose values using hardware-specific conventions.

## Driver Diagnostics

### Driver Age

Driver installation or metadata dates do not automatically indicate that a driver is obsolete.

An older driver can remain appropriate for a specific system.

### Driver Signing

An unsigned driver is not automatically malicious or defective.

Some legitimate environments may contain specialized or vendor-specific drivers with different signing characteristics.

### Driver File Existence

`Test-Path` confirms whether a referenced file exists.

It does not verify:

* File integrity
* Digital signature validity
* Driver functionality
* Driver authenticity

### Duplicate Entries

Multiple driver entries grouped by device name do not necessarily represent conflicting driver installations.

They may reflect legitimate driver packages, versions, or device configurations.

### Boot-Critical Metadata

Boot-critical driver metadata indicates driver classification information.

It does not measure actual boot-time driver loading latency.

## Battery Diagnostics

### Battery Report Parsing

Battery capacity and wear information is extracted from the Windows battery report.

The implementation depends on the report structure generated by Windows.

### Wear Level

Battery wear is estimated from:

```text
1 - Full Charge Capacity / Design Capacity
```

This is an estimate of capacity degradation, not a complete assessment of battery health.

### Cycle Count

Cycle count is only available when the system firmware or WMI provider exposes the relevant information.

### Discharge Rate

Power-draw information depends on the availability and behavior of the Windows power-meter provider.

The module's discharge threshold is heuristic and is not universal across laptop classes.

### Battery Temperature

Battery temperature is only reported when an ACPI thermal-zone source can be associated with the battery.

### Battery Score

The battery score is a heuristic score derived from selected conditions.

It should not be interpreted as an official battery health percentage.

## Storage Diagnostics

### Disk Performance

Read/write performance values are short performance-counter observations.

They are not equivalent to a storage benchmark and should not be used to compare drive performance under controlled conditions.

### SSD Detection

SSD identification uses hardware metadata and naming heuristics.

Some devices may not be classified correctly.

### Physical Disk Health

`MSFT_PhysicalDisk` health information depends on the storage stack and device support.

It should not be treated as a complete SMART diagnostic.

### Large File Analysis

The large-file scan is limited to the configured system drive and therefore does not provide a complete inventory of all large files across every volume.

### Temporary Files

Temporary-file measurements depend on the execution context and filesystem accessibility.

A file being classified as temporary does not necessarily mean that it is safe or desirable to delete.

## Security Diagnostics

### Suspicious Process Detection

The suspicious-process analysis uses heuristics such as:

* Missing company information
* Process location
* Known Windows paths
* Program Files locations
* A predefined safe-process list

These conditions can produce false positives and false negatives.

### Network Port Detection

The module checks a predefined list of ports associated with potentially suspicious activity.

A connection involving one of these ports is not evidence by itself of malicious activity.

### Connection Counts

A high number of established connections does not inherently indicate a security problem.

Legitimate browsers, synchronization tools, games, communication applications, and system services can maintain many connections.

### Recent Executables

Recently modified executable files may represent:

* Legitimate software updates
* Driver updates
* Installers
* System maintenance
* Normal application activity

Recent modification alone does not establish malicious behavior.

### UAC and Uptime

Disabled UAC or long system uptime can be useful audit indicators, but neither condition independently establishes that a system is compromised or insecure.

### Security Score

The security score is heuristic and should not replace antivirus software, endpoint protection, vulnerability assessment, or professional security analysis.

## Registry Startup Diagnostics

### Startup Coverage

The module examines selected Registry `Run` and `RunOnce` locations.

It does not provide complete Windows persistence analysis.

Other persistence mechanisms include:

* Scheduled tasks
* Services
* Drivers
* Startup folders
* WMI subscriptions
* Browser extensions
* Other registry locations

### Executable Classification

The classification:

```text
SYSTEM_CORE
ACTIVE
USER_OPTIONAL
```

is based on path characteristics.

It does not establish whether an executable is trusted, necessary, or safe.

### Path Extraction

The current implementation primarily attempts to identify `.exe` paths.

Complex commands, scripts, launchers, environment-variable expansions, and other command structures may not be classified correctly.

## Cache and Recycle Bin Diagnostics

### Filesystem Scan Cost

Recursive filesystem enumeration can be expensive on large directories or systems with many files.

### Browser Cache Coverage

The current implementation targets selected default browser cache paths.

It does not necessarily cover:

* Every browser
* Every browser profile
* Portable installations
* Custom cache locations

### Cleanup Classification

Reported cache or temporary data represents potentially reclaimable data.

The diagnostic does not guarantee that every detected file can or should be deleted.

### Thresholds

Cache and cleanup thresholds are heuristic values intended to identify potentially significant storage usage.

They are not universal system-health thresholds.

## Windows Update Diagnostics

### Log Generation

Windows Update log generation depends on the availability and behavior of the Windows diagnostic tooling.

### Keyword Matching

The module searches for predefined keywords.

Keyword matches do not necessarily correspond to actual errors or root causes.

### Output Limit

The module limits displayed matching lines to prevent excessively large reports.

Therefore, the displayed matches may represent only a subset of all matching entries.

## JSON Limitations

JSON output is designed for structured consumption, but the first edition does not define a universal schema across every diagnostic domain.

Some values may be:

* `null`
* Missing when unavailable
* Heuristic classifications
* Hardware-dependent
* Snapshot measurements

Consumers should therefore validate field availability before using values programmatically.

The JSON marker extraction mechanism currently expects a structured JSON block between:

```text
---JSON_START---
---JSON_END---
```

and the Python engine is designed around this convention.

## Administrative Privilege Limitations

Some diagnostics provide different results depending on whether the application is executed with administrator privileges.

A non-administrative run may therefore contain incomplete information without indicating an actual system fault.

## Network Dependency

Some diagnostic operations may rely on external network connectivity.

For example, latency diagnostics may use an external host for ICMP measurement.

Network-based measurements represent the path to the selected external host and are therefore not equivalent to purely local network latency.

## Snapshot Nature

Most diagnostics are short-lived snapshots.

They do not continuously monitor the system over extended periods.

Consequently, intermittent problems may not be observed during a single audit run.

For issues that depend on workload, thermal history, network conditions, or long-term reliability, repeated measurements over time may provide more representative results.

## Not a Security Product

The framework should not be considered:

* An antivirus product
* An endpoint detection and response platform
* A vulnerability scanner
* A malware analysis framework
* A forensic investigation platform

Security-related results are diagnostic indicators intended to assist system inspection.

## Not a Hardware Benchmark

Performance values should not be interpreted as standardized benchmarks.

Controlled benchmarking requires defined workloads, repeated measurements, environmental controls, and hardware-specific methodology.

## Future Improvements

Potential future improvements include:

* More reliable hardware sensor interfaces
* Better Windows-version compatibility
* Explicit capability detection
* Improved error reporting
* More precise performance sampling
* Hardware-specific sensor providers
* Expanded persistence analysis
* Standardized JSON metadata
* Schema versioning
* Historical result comparison
* Long-term monitoring
* Cross-module correlation
* Automated diagnostic analysis
* Optional LLM-assisted interpretation

These improvements should be introduced as deliberate functional or architectural changes rather than being assumed to exist in the current edition.
